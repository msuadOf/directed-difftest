# RTL 疑点定向 DiffTest 验证工作流（简版）

一页纸速览。详细设计见 `workflow-detailed.md`。

## 流程图

```
 输入: suspicions[{id,file,line,claim}] + max_rounds + workspace
   |
   v
+--------------------------------------------------------------+
| 1. Hypothesize  每疑点1个agent只读RTL，产出可判定假设          |
|    trigger / expected / masking / testability / sensitivity   |
+------------------------+-------------------------------------+
                         | reachable/masked-reachable 才进仿真
                         | unreachable 直接跳到 Skeptic
                         v
+--------------------------------------------------------------+
| 2. Probe  构造汇编自检用例 + 灵敏度对照，首测 DiffTest          |
|    + 无条件一致性追问(trap/flushPipe/vsetvli后读回架构状态)     |
+------------------------+-------------------------------------+
                         v
+--------------------------------------------------------------+
| 3. Isolate  JS循环驱动，每轮只改一个变量                       |
|    归因: wrong-target-write / bypass-checkpoint-pollution     |
|          / commit-timing / not-reproducible                   |
|    终止由代码判: 轮数上限 或 连续一轮无新信息                  |
+------------------------+-------------------------------------+
                         v
+--------------------------------------------------------------+
| 4. Skeptic  专门推翻结论: 重跑最小复现、验证对照真实性、        |
|    逐行核对"机制规避"依赖的机制代码                            |
|    verdict: CONFIRMED / REFUTED / DOWNGRADED                  |
+------------------------+-------------------------------------+
                         v
+--------------------------------------------------------------+
| 5. Synthesize  barrier 汇总: 三分类表 + 证据链 + 复现清单      |
|    + 覆盖面声明 + findings.md 条目草稿(只出草稿)               |
+--------------------------------------------------------------+
```

各疑点独立流水线，互不等待，只在最后 barrier 汇总。

## 每阶段一句话

1. **Hypothesize**：读 RTL，把疑点翻译成可判定的假设（怎么触发、预期错什么、是否被掩盖）。
2. **Probe**：首测——自检用例 + 灵敏度对照 + 一致性追问（被掩盖的原疑点路径后面常藏真 bug）。
3. **Isolate**：变量控制迭代，每轮只改一个变量，把复现归因到四类之一，时通时不通记触发率判竞态。
4. **Skeptic**：对抗复核，专门尝试推翻结论；REFUTED 不回环、标人工复核。
5. **Synthesize**：barrier 汇总成三分类结论 + findings 草稿。

## 三分类结论

| 分类 | 含义 |
|---|---|
| 真实可触发（bug） | 有 DiffTest ABORT / 数据分歧证据 + 最小复现 ELF |
| 被机制天然规避 | 写明是哪条机制代码拦截的（须逐行核对过） |
| 当前配置不可达 | 写明何时会暴露（如换 VLEN/配置参数后） |

## 动机实例

三个实测疑点恰好各落一类：S1 vstart 硬编码被 illegal 检查掩盖、但掩盖路径中测出 tail-agnostic 污染真 bug；S2 vxsat 顺序问题被 CSR `noSpec+blockBack` 机制天然规避；S3 ByteMaskTailGen VLEN 硬编码当前配置不可达。完整案例见 [motivation.md](motivation.md)。

## 关键教训

1. **测试通过 ≠ 无 bug**：疑点被证伪时，必须追问 trap 返回、flushPipe、vsetvli 重配置之后架构状态是否一致——真 bug 常藏在掩盖原疑点的路径里（S1 即如此：原命题被掩盖，掩盖路径才是真 bug）。
2. **灵敏度对照**：自检用例可能恒真。必须先跑一个"已知应有差异"的对照（如不执行清零指令确认状态真被改变），否则结论无效。
3. **循环终止由代码控制**：Isolate 迭代不让 agent 自己决定"差不多了"——由 JS 循环按"轮数上限 + 连续一轮无新信息"客观终止。
4. **决定性实验定根因**：读一个从未被写过的相邻寄存器仍出错（S1 的 t16），即可区分"写错目标"与"旁路/检查点污染"。
