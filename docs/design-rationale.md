# 设计讨论记录：并行化与看门狗（2026-08-25 架构重构）

本文是 2026-08-25 架构重构的**决策记录**：记下当时的问题、双方的原始想法、实测如何校准了直觉、以及每一轮讨论把设计推到哪里。规范性设计见 [workflow-detailed.md](workflow-detailed.md)；本文回答"为什么是这样设计的、否决了什么、为什么否决"。

## 一、起点：两个痛点（用户提出）

1. **跑一次 workflow 时间长**，大头是处理器仿真跑程序慢。用户初始设想：仿真可以并行或流水线——"一个 emu 可能只吃 4 线程，12 核就可以跑 3 个实例"。
2. **挖 bug 不深入**。用户判断：不止是迭代次数问题，还有调度机制问题——应该把波形、处理器 itrace（指令流记录）、处理器状态收集起来分析，寻找有线索的异常；可能需要重新思考架构流程。

## 二、实测校准（动手前先量，三处直觉被修正）

| 假设 | 实测 | 对设计的影响 |
|---|---|---|
| "一个 emu 吃 4 线程，12 核跑 3 个" | emu 虽以 `--threads 4` verilate（`VSimTop::threads()==4`，NLWP=12），**实际只有 1 个线程热，99% 单核** | 并行度上限不是 3 路而是 **8-10 路**，收益比预想大 3 倍 |
| 慢在仿真本身 | 启动开销仅 ~1.1 s；稳态 ~250-300 cycles/s；平均 25.3 s/次（历史 516 次，累计 218 分钟） | 每 cycle 的仿真速率改不了，只能并行摊薄；**合并小用例省启动不划算**（1.1 s 换隔离性受损，不值），批量并行才是对的 |
| （未预料）尾部损耗 | 最长一次 **525 s**——挂死用例烧满外层 timeout；讨论当时还有一个跑了 7 分钟的无 `-C` 上限流浪 emu | 挂死尾巴比正常用例更浪费；催生了看门狗这条线 |

另一个关键发现：旧 workflow 的慢不在 Workflow 层（疑点间本就并行），而在 **agent 内部**——一个 agent 写了 scan1~scan8 逐个串行跑（8×15 s 纯排队），Isolate 又是"每轮 spawn 一个 agent 只改一个变量"的串行大循环。

> **数据来源**：516 次/25.3 s/218 分钟/最长 525 s 来自对 artifacts/ 历史日志的 `Host time spent` 汇总（grep 于 2026-08-25，artifacts 已 gitignore，清理后不可复算——独立评审当日复核为 524 个日志/25.1 s/219 min/524.7 s，吻合）；emu 单核占用（99%/NLWP=12/`--threads 4`）、启动 ~1.1 s、批测 CPU 329% 为当日一次性运行时观测，无仓库留痕，属孤证。

## 三、提速设计（回应痛点 1）

1. **批量并行 runner**（`scripts/run_batch.py`）：一批 `.S` 一次提交，flock 全局槽位（默认 8 槽，其中 1 槽保留给误杀重跑插队，普通批次 7 路并行；跨 agent 共享——否则 N 个 agent 各开 M 个 emu 会压垮 12 核）。agent 从"跑 8 次等 8 次"变成"提交一批、读一张表"。
2. **Isolate 串行轮 → 批次轮**："一次只改一个变量"是**归因纪律，不是执行顺序约束**——一轮设计 3-6 个彼此正交的单变量变体并行跑，4-8 轮串行收敛的内容 1-2 轮完成。这也是用户"流水线"直觉的正确形态：真正值得重叠的不是编译和仿真（编译 <1 s），而是 **agent 思考与仿真执行的重叠**。
3. **挂死尾巴主要由绊线砍掉**（实测击毙在 12-30 s），`-C`/`--wall` 只是兜底——默认值（120000 cycles / 600 s）下兜底本身仍是 8-10 分钟量级，作用是"绊线万一漏了也有硬上限"，不是主力止损。
4. 未采纳/暂缓：合并多用例进一个 ELF（省 1.1 s 启动、赔隔离性，否）；boot 快照恢复（`--enable-snapshot`，与 difftest 兼容性未测，先放）。

## 四、深挖设计（回应痛点 2）

诊断：深挖不足的根源不是迭代次数，是**证据被囚禁在单个 agent 的上下文里**——每次仿真产出的丰富信号（提交跟踪、REF 跟踪、架构状态、周期数、波形）穿过 schema 只剩几句话；跨 run/跨疑点的模式没有机制能看见；"解释不了的观察"没有去处。S1 的教训（真 bug 藏在"原假设被证伪后的一个顺手观察"里）在旧版只固化成一个固定步骤（一致性追问），没有泛化成机制。

落地为三层架构（用户"收集波形/itrace/状态做关联分析"的制度化）：

- **证据层**：每次仿真一条结构化记录进 runs.jsonl（参数、终态、首分歧、周期数、签名），跨 run 模式变成可查询问题。
- **分析层**：确定性蒸馏工具——trace_diff（双跟踪对齐找控制流首分歧，比 difftest 的架构分歧更接近根因）、vcd_extract（波形窗口→CSV，agent 不啃原始 VCD）、runs_query --outliers（周期数离群 = 波形"自对照不一致"判据的廉价前置过滤器）。
- **决策层**：Probe/Isolate 两阶段强制上报 anomalies（Diagnose 重放确诊的真挂死也进池）→ 跨疑点异常池 → Triage 聚类晋升新疑点（带证据进下一 sweep，不再一句话从零跑）；确定性复现解锁深挖（双跟踪差分+最小化）。

## 五、看门狗：四轮对话的演进（本次讨论的核心增量）

### 第 1 轮——用户提议：定时看门狗 subagent

> "需要一个看门狗 subagent 固定时间（如 5 分钟）看看波形，看处理器是否卡死；对照代码和反汇编、看 itrace 输出，判断处理器是否跑到非预期的地方。"

**回应：方向对，机制拆两半——检测用脚本、诊断用 subagent。** 理由：(a) "卡没卡死"的信号完全机械，脚本 10-15 s 粒度（落地为 8 s 轮询）对 5 分钟粒度是 20 倍以上改善（平均一次仿真才 25 s，5 分钟粒度意味着大部分挂死照样烧满 5 分钟）；(b) 全程开波形代价太高（拖慢数倍+几十 MB 文件），而 **Verilator 确定性**允许事后按需重放取波形，平时零开销；(c) LLM 的价值在"为什么挂"，事件触发即可。并给出挂死四分类（自旋/跑飞/慢但在走/真死锁），前三类纯脚本可判——"对照反汇编看 itrace"这一步大半可确定性化（commit pc → objdump 符号映射）。

### 第 2 轮——用户质疑：纯脚本会误判

**承认误判场景真实存在**（历史用例里就有压力循环，与 `j .` 自旋在 trace 上长一样；`-b/-e` 日志窗口假象；宿主机负载假象；偶发退休的活锁漏报），**但解法不是换更聪明的检测者，而是把误判的杀伤力拆掉**：

- 绊线从"裁判"降级为"绊线"：只判"可疑"，不下定论；
- 第一动作 SIGSTOP 无损暂停（当时的方案），误报 SIGCONT 原地继续；
- 机械化消掉大部分误报源：runner 统一接管 `-b/-e`（消日志窗口假象）、CPU 时间域测进度（消宿主机负载假象）、**写回值进展检查**（延时循环 data 每轮变化→放行；两条指令的无写回自环→击毙。注意单条 `j .` 到不了看门狗——emu 把 jal-to-self 直接判 GOODTRAP，这正是模板要求 FAIL 自环用两条指令的原因）、`POLL_` 标签意图声明（写用例的人最清楚哪个循环是故意的，这个信息以前被白白扔掉）；
- 误判可审计：每次触发进 runs.jsonl，516 次历史 run 是现成标定集，阈值可持续校准；看门狗结论永远标"机检初判"。

### 第 3 轮——用户提议：write-back 语义

> "类似 cache 的 write back：先脚本快速杀住，然后进行下一个，同时开 subagent 复核。"

**接受，且优于第 2 轮的 SIGSTOP 方案**：SIGSTOP 让可疑 run 占着槽位等裁决，吞吐被复核延迟绑架；write-back 把"止损"和"裁决"解耦——杀住、槽位立刻还给下一个用例、复核异步。支撑它成立的仍是确定性：**误杀无损，大不了重放**。补齐四个细节：SIGINT 体面杀+标准化证据打包（复核面对证据包而非活进程）、复核攒批（当时的方案）、防乒乓（误杀重跑必须带修正且封顶 2 次）、批次结果允许"带洞"。

### 第 4 轮——用户修正：一杀一审，不攒批

> "要一杀一审，因为有的工序需要等待仿真的结果。"

**接受，收回攒批**：Probe/Isolate 拿仿真结果做下一步决策，一个 pending 复核就是一条卡住的流水线；杀是稀疏事件，单审成本付得起，攒批省 agent 成本赔的是关键路径延迟——方向反了。最终定稿三个配套：

1. **终态收敛契约**：`killed-suspect` 不是终态，每个用例最终恰好收敛到一个终态，看门狗机制对消费端透明。收敛落到两层：workflow 输出层（hang_reports 裁决），以及证据层——复核 agent 用 `runs_query.py --resolve` 追加销案记录（append-only），`--pending-review` 队列因此真正收敛而非只增不减；
2. **重跑插队**：FALSE_KILL 重跑有下游在等，走保留的优先槽位（槽位 0）；
3. **同签名合并（MSHR 语义）**：一批 8 个用例因同一系统性原因全挂时，同 `sig_id` 只审一次、裁决套用全部——不是攒批（不同签名仍即杀即审），是合并完全相同的 miss。签名 locus 按**符号名去偏移**归一化——不同变体代码长度不同导致停驻偏移不同（`_start+0x4c` vs `+0x50`），带偏移的签名会让同根因变体各成一签、合并失效；精确偏移仍保留在证据包里。代价是反向的**过合并**风险（两个不同根因恰好同停在 `_start` 会共 sig_id）——所以合并审理时仍须扫一眼各用例的 evidence 确认现象确实相同，签名只是合并的候选依据。

**最终形态**：`-C` 兜底 → 绊线快杀放行下一个（write-back）→ 拥有该用例的 agent 即时一杀一审（它在等结果、有全部上下文、零交接成本；同签名合并）→ 仍 UNCLEAR 派专门 Diagnose agent（确定性重放+波形）→ 裁决双向回流（TRUE_HANG→签名库秒判 / FALSE_KILL→绊线校准；销案经 `--resolve` 写回数据库）。用户最初设想的 subagent 该干的事（对照反汇编、看 itrace、看波形）全部保留，只是触发方式从定时器换成绊线、且大半检测被确定性化。

**机制的强制层级**（读本文时须区分，误判后果不同）：**runner 硬强制**——槽位/`-C`/绊线判据/证据包/签名/`review=pending` 标记；**workflow JS 硬强制**——批次轮终止条件、Diagnose 插入、异常池收集、队列去重；**prompt 软约定（依赖 agent 自觉，由 Skeptic 与 Synthesize 的 watchdog_notes 事后审计）**——一杀一审本身、FALSE_KILL 重入队封顶 2 次、同签名合并、Triage 晋升上限 5 条、`--resolve` 销案。

## 七、放弃、边界与留作后续

- **SIGSTOP 无损暂停方案**：被 write-back 取代（占槽位）；若未来出现"重放太贵"的超长 run，可重新评估对这类 run 用 SIGSTOP。
- **"误杀无损"的边界**：整条 write-back 链（先杀后审、事后取波形、Skeptic 重跑）的承重假设是 **Verilator 同 seed 确定性**，仓库尚无确定性自检（同一用例两跑比对 cycleCnt）；且"无损"准确说是**有界损耗**（一次重跑 + 一次复核）。write-back 的"槽位立刻放行"收益以批为界——run_batch.py 同步返回，批内最后一个用例被杀时对拥有者 agent 不省时间，省的是槽位（其他 agent 受益）。
- **STALL 检测盲区**：判据要求已有 ≥1 条提交——首条提交前就死住的进程（如加载/difftest 初始化卡死）只能靠墙钟兜底。
- **跨 agent 的 pending 复核合并**：当前同签名合并只在单 agent 的批内生效，跨 agent 靠签名库匹配兜住（runner 自动标 `known_hang`）；真正的跨 agent pending 表未实现，观察实际是否需要。
- **boot 快照恢复**（省每 run 千余 cycle 的引导）：与 difftest 兼容性未测。
- **全自动 ddmin 最小化**：当前由 Isolate agent 用批次驱动（删减出 3-5 个候选并行跑）；如量大再脚本化。
- **STALL 的 cycle 域心跳**：emu 无周期性输出，现用 /proc CPU 时间做代理；若误判集中在此，考虑给 emu 加轻量心跳输出。
